# SPLADE 补充解读：把语义装进倒排索引

> 本页是机制与部署分析，不把推导例子当作论文实验。

## “稀疏”与“语义”可以同时成立

BM25 的维度通常由原文词项决定。SPLADE 的维度仍有词项含义，但激活哪些维度由上下文网络决定。例如描述“修理汽车”的段落可能在 car 之外激活 vehicle、repair 等维度。查询也做相同词表空间映射，最后相同维度的权重相乘。

因此它的“精确匹配”是**扩展后词表坐标的精确匹配**，不等于相关文档必须含有查询原字面词。也不是把 768 维稠密 embedding 做阈值置零：这里的 30,522 维从一开始就对应 MLM 词表。

## 为什么平均非零数还不够

考虑两个索引，都让每篇文档激活 100 个词。索引 A 的词项均匀分布；索引 B 几乎每篇都激活同一个高频词。查询命中这个高频词时，B 可能需要遍历很长的 posting list，远比 A 慢。FLOPS 正则对 batch 平均激活的平方惩罚，试图减少这种集中现象。

不过它不是精确的服务延迟模型。缓存命中、压缩方式、跳表、WAND、并行度和查询分布都会影响实际时间；换一个检索引擎，相同稀疏统计也可能有不同延迟。

## 词项权重不是词概率

logits 经过 ReLU 和 log1p 后没有归一化到总和为 1。一个文档可以同时为多个语义相关词赋较大权重，长度也会影响 sum pooling。它应理解为学习到的检索权重，而不是“这个词在文档里的概率”。

扩展词也不一定可自然拼成一句话。解释检索命中时最好同时展示原文证据和高贡献词项，避免把扩展列表当作原文事实。

## 工程上怎样比较 dense、sparse 与 hybrid

在同一语料切分、同一查询集合上测 Recall@k、nDCG@k、索引占用、编码耗时和 P95 查询延迟。SPLADE 的主要优势是学习词项扩展同时沿用倒排结构；稠密模型的优势是较紧凑的单向量语义空间；hybrid 的价值需通过互补召回来验证。

别直接相加未经校准的 BM25、SPLADE 和余弦分数。可以先用 RRF 等排名融合建立基线，再在验证集上学习融合权重。这个建议是部署实践推导，不是原论文报告的实验。
