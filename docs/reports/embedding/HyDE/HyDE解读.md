# HyDE 补充解读：先猜一种证据的样子

> 本页讨论直觉、失效情形与工程选择，区别于论文实验。

## 为什么不是直接相信生成答案

用户问“某种合金为什么在低温下变脆”，短问题的表面形式与材料论文段落差异很大。生成器先写出可能包含晶体结构、裂纹传播等概念的段落，编码器就能在“文档式文本”的空间中寻找真实材料。假想文本的用处在于提供相关性线索，不在于替代证据。

实际系统应该让最终回答依据检索到的原文。若把假想文档混进引用资料，容易把中介步骤的猜测伪装成外部证据。

## 三种生成增强并不一样

| 方法 | 何时生成 | 改变什么 |
|---|---|---|
| Doc2Query | 建库时 | 扩充文档侧词项或表示 |
| InPars/GPL | 训练时 | 构造检索／重排监督 |
| HyDE | 查询时 | 改造这一条查询的向量 |

因此 HyDE 不必重训，但会增加每次查询的生成开销；离线方法相反。成本要按查询量、建库频率和延迟预算比较。

## 平均向量为什么可能失败

假设“苹果的增长”既可能指水果产量，也可能指公司营收。两种假想文档的平均向量不一定对应任何一种真实需求。可以先澄清意图，或分别检索多种假设后融合候选；这属于扩展方案，不能说原论文已经证明其效果。

保留原始查询的召回通道也有价值，尤其是型号、专有名词、代码、精确数字。生成器改写掉这些细节时，原查询或稀疏召回可提供互补。

## 与一个强现代 embedding 搭配时如何判断收益

用同一个文档索引做四组对照：原查询、假想文档、两者平均、双通道候选融合。固定候选数并记录 Recall@k、最终 nDCG、生成失败率和 P95 延迟。还应单独看实体查询、领域长尾和否定条件，避免平均收益掩盖某类请求变差。

不要把“生成文本看起来更专业”作为检索有效的证据。真正的判断标准是找到的真实文档是否更符合需求。
