# Cordis：补充解读

> Python使用者怎样理解受管清理与动态依赖？以下为直觉解释与应用延伸，论文内容见 [精炼主笔记](Cordis详解.md)。

## Python 视角：ExitStack 只解决了问题的一半

`contextlib.ExitStack` 能集中保存清理回调，作用域退出时逆序执行，很接近可撤销 effect 的直觉。但它并不知道某个插件依赖数据库服务，也不会在数据库配置替换时自动停用、重新激活依赖者。Cordis 的另一半是随上下文变化而更新的依赖关系。

因此，给 Python 插件套一层 `with` 有价值，却不等于实现了完整的动态组合系统。资源作用域、服务依赖与重新激活顺序必须一起设计。

## “可撤销”不等于数据库事务

注册一个事件监听器后可以注销；创建定时任务后可以取消尚未触发的任务；发送一封邮件后无法让收件人没有收到。前两类可以在受管上下文中表达明确清理，后一类通常只能通过补偿动作缓解后果。

这也是论文使用观察等价而非全世界状态回滚的原因。将幂等、补偿和可逆操作混为一谈，会高估系统给出的保证。

## 为什么依赖停用顺序比依赖注入更难

假设插件 B 正在使用服务 A。替换 A 时，先清掉 A 再通知 B，会留下一个失效引用窗口。更可靠的过程是先停止 A 接受新依赖，使 B 退出并释放引用，随后移除 A；新 A 就绪后再让 B 激活。

复杂性来自异步任务和进一步依赖 B 的 C。局部清理函数正确，并不足以推出整个依赖网络正确；论文的大量形式化篇幅正是在建立这种组合条件。

## 对 Agent harness 的启发

长时间运行的 Agent 会动态加入工具、凭据作用域、检索连接与监控。可以借鉴的是统一注册、显式依赖和可追踪清理，而不是把 Cordis 当作推理算法。涉及真实交易、外部写入或用户消息的工具，仍要单独设计幂等键和补偿策略。

阅读顺序可先看概念、生命周期图、实现与案例，再回到演算。证明主要回答“在什么约束下可组合”，实践主要回答“怎样让组件遵守这些约束”。

## 用一个具体场景串起来

ExitStack能把一组资源按逆序释放，适合局部时间作用域；长期插件还要知道数据库服务换实例时，哪些组件必须先停再重启。后者是依赖视图与生命周期问题，不是多加几个finally就够了。

若插件A保存整个注册表旧快照，卸载时覆盖恢复，会删掉B后来加的项；若A只撤销自己那条带标识的注册，就更可能与B独立。这体现为什么可逆操作还需要合适表示和独立性。
