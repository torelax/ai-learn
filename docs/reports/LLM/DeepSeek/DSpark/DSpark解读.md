# DSpark：补充解读

> 为什么不能看完整草稿后再随意决定前面收不收？以下为直觉解释与应用延伸，论文内容见 [精炼主笔记](DSpark详解.md)。

## 接受长度最大不等于吞吐最大

如果多验证三个几乎必被拒绝的 token，就占用了其他请求能用的容量。空闲时这点计算可能便宜，拥堵时却很贵，所以固定最长草稿不一定是最优策略。

![并行骨干和轻量序列依赖](figs/S3-F1-01.png)

图中把复杂上下文理解放到并行部分，把局部续写一致性放到轻量头。这比完全独立预测更能避免混合两条不同续写路径。

## 前缀概率为何是连乘

验证在第一次拒绝处停止。即使第 5 个 token 单独看很有把握，前四个有一个失败，它也不能被直接跳过来接受。因此调度要使用整段前缀存活概率，而不是每个位置各自的置信度。

## “无损”需要算法和实现同时成立

目标模型仍负责最终接受/纠正，理论上可以保持原采样分布。若调度器窥视未来候选后再决定是否验证，可能引入选择偏差。论文的异步安排不仅为吞吐服务，也在管理这种依赖关系。

## 用一个具体场景串起来

若第二个候选token是某个词时才允许第一个候选进入验证，准入事件已经携带后续随机样本的信息。即使每个被验证token使用标准接受公式，也可能改变整体输出分布。

因此自适应长度需要non-anticipating条件。DSpark把理论早停和生产历史容量调度分开论证；“验得少更快”是性能直觉，“仍严格目标分布”则需要另一个数学条件。
