# DeepSeek-V4.1-Flash：补充解读

> 预填充省一半计算与缓存精确恢复为何不能混为一谈？以下为直觉解释与应用延伸，论文内容见 [精炼主笔记](DeepSeek-V4.1-Flash详解.md)。

## “prefill 8B，decode 16B”从何而来

不是每个 token 随机选择不同模型，而是上下两半网络在两个阶段的职责不同。全局 KV 可由 encoder 输出构建，prompt 的大部分位置不必做完整 decoder 计算；生成新 token 仍需要更完整的网络。

![CED 与共享注意力](figs/S1-F3-01.png)

图中的局部窗口是例外：它需要当前层状态，因此要通过重放处理。忽略这部分，就会把“接近减半”错误解释为严格省掉一半所有成本。

## 缓存的四个维度

每条目的维度、条目数、层数、精度都可压缩；生命周期决定缓存放在哪里。CSA2、FP4 与 SWA 管理分别改变不同维度，因此收益可以组合，但不能把 HBM 字节数和 SSD 持久容量混为同一个指标。

## 近似重放是一个可测的工程取舍

截断窗口依赖后恢复的状态不必与完整运行 bitwise 相同。是否值得，要在真实会话的 cache miss 比例、恢复时延和回答质量之间验证。论文展示一种部署选择，而不是所有应用都应接受的默认设定。

## 模型与 harness 都决定 agent 成绩

工具 schema、上下文整理、重试与执行预算会改变任务完成率。复现时固定 checkpoint 远远不够，还应记录 harness 版本与任务环境；这一点在本篇跨框架对照中有直接证据。

## 用一个具体场景串起来

CED让prompt的大部分token只跑encoder，为decoder构建全局KV；局部SWA仍需后半网络状态。只重放最近窗口省成本，却截掉更早的跨层依赖，所以恢复是近似的。

这项取舍应测质量、miss延迟和命中位置敏感性。它与跨层共享、FP4、Engram查表是不同维度，不能把各自节省比例简单相乘为最终吞吐，最终还受带宽、batch和harness控制。
